## Overview

Blog API is a publishing system composed of three independently runnable applications: an Express API, an author dashboard, and a public reader experience. The separation forces the backend contract to be real—publishing, ownership, comments, and moderation cannot depend on privileged client-side assumptions.

## Features

- Registration and login with differentiated `AUTHOR` and `USER` roles.
- Author-owned post creation, editing, deletion, drafting, and publication.
- A public paginated feed that exposes published content only.
- Reader comments with edit and delete ownership rules.
- Author moderation over discussion attached to owned posts.
- Separate responsive author and reader applications consuming the same API.
- Rate limiting around authentication and comment traffic.

## Architecture

The system uses a client/API boundary rather than embedding publishing logic inside one interface. Express routes and middleware delegate to controllers around Prisma, while the author and reader React applications consume the same documented REST resources. PostgreSQL relationships connect users, posts, and comments; publication state and timestamps make editorial lifecycle explicit.

## Challenges

The main challenge was expressing authorization beyond authentication. Being logged in is not enough to edit a post, moderate a comment, or expose a draft. Each mutation needed role and ownership rules, while the public client required a deliberately smaller view of the same data. Keeping two clients synchronized with an evolving API also made documentation and stable response shapes important.

## Lessons learned

Separating the clients made security boundaries visible. Draft state belongs in the data model, ownership belongs in server-side checks, and pagination belongs in the API contract. Rate limits around sensitive routes added practical defense in depth, while the multi-client structure demonstrated that the backend could support more than one presentation layer.
